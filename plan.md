# Plan: StarSync — Daily Vedic Astrology Product for Gen-Z/IT Professionals

**Date:** 2026-09-30
**Status:** Updated — 2026-10-01 (v3 — full UI redesign, see Design direction below)

## Context

`modern-raasi-palan` is currently an empty repo. The goal: a fun, Gen-Z/IT-coded daily astrology
product — "raasi palan" (Tamil daily rasi predictions), modernized. Users complete a single
onboarding page (name, email, DOB, time of birth, place of birth, role/profession, preferred send
time), get a 5-day free trial, then are billed ₹11.11/week via UPI Autopay (or card) through
Razorpay. Daily content is generated by Claude and emailed at the user's chosen time, contextualized
to their profession. Privacy is a core pitch: birth data is encrypted and never seen by a human.

Decided with the user already:
- **Name / domain:** StarSync → `starsync.familyfirstapps.com`
- **Payments:** Razorpay (UPI Autopay + card subscriptions)
- **Privacy framing:** "Encrypted, never seen by a human" — not literal zero-knowledge. The backend
  necessarily decrypts data transiently to auto-generate content and auto-charge; we're honest about
  that instead of over-promising.
- **Astrology system:** time-of-birth + place-of-birth being required (not just DOB) confirms this is
  Vedic/sidereal Rasi (moon-sign) + Nakshatra astrology, not Western sun-sign.

Technical feasibility research (completed) resolved three open architecture questions — see below.

## Architecture

**Single Cloudflare project, one repo:** Astro with the `@astrojs/cloudflare` adapter, deployed as one
Cloudflare Pages project. Astro server endpoints act as the API (no separate Workers project needed),
bound to D1, a Queue, and secrets.

- **Frontend:** Astro + plain CSS.
- **DB:** Cloudflare D1 (`db/schema.sql`).
- **Astrology calculation — computed in-process, no third-party API** (`src/lib/vedic.ts`). Revised
  from the original plan: this product's daily content is entertainment/affirmation-style ("what to
  do and not do today"), not a claim of professional predictive accuracy, so paying a per-request
  astrology API (evaluated: AstrologyAPI.com's Ruby/Emerald/Sapphire tiers, $19–99/mo; ProKerala is
  similarly credit-metered) isn't worth it — especially since that pricing is for *daily horoscope
  generation* requests, an endpoint we were never going to call per-day anyway (we only needed a
  one-time-per-signup birth-chart lookup, whose credit cost wasn't even shown on the pricing page we
  were quoted). Instead we compute the Moon's sidereal longitude ourselves using the `astronomia`
  npm package — a pure-JS, no-data-files port of Meeus' *Astronomical Algorithms* ch. 47 lunar theory
  (accurate to a few arcseconds) — minus an approximate Lahiri ayanamsa, to get Rasi + Nakshatra +
  pada. This is $0 recurring cost, no vendor dependency/latency/downtime risk, and — as a nice side
  effect — one fewer third party ever touches birth data at all (see the updated privacy page). We
  don't compute the Lagna/ascendant: traditional daily "raasi palan" content is keyed off the Moon's
  rasi, not the ascendant, so nothing needs it, and dropping it avoided a materially harder
  calculation (ascendant needs precise local sidereal time + geographic latitude).
- **Geocoding + timezone resolution:** free-text place of birth → lat/lng via the free, keyless
  Open-Meteo Geocoding API, then lat/lng → IANA timezone via the offline `tz-lookup` package, then
  `Intl.DateTimeFormat` resolves that timezone's UTC offset for the birth date — giving `vedic.ts` an
  accurate UTC birth instant to compute from (`src/lib/geocoding.ts`). Still needed even without
  ProKerala, since converting "2pm in [city]" to the correct UTC instant requires knowing that city's
  historical offset. No paid API/account needed for this step.
- **Payments:** Razorpay Subscriptions (`src/lib/razorpay.ts`). Trial via `start_at` (now + 5 days) on
  `subscriptions.create` — no charge until then. UPI Autopay e-mandate + card e-mandate both supported
  in the same flow; ₹11.11/week is well within the ₹15,000 frictionless-debit limit.
  **Open question to confirm in the Razorpay dashboard:** whether UPI Autopay mandate registration
  triggers a small visible authorization charge during signup even though the trial itself is free —
  affects trial copy and must be checked before launch.
  Webhooks still to implement (not built this pass): `subscription.authenticated`, `.activated`,
  `.charged`, `.pending`, `.halted`, `.cancelled`, `.paused`/`.resumed`, `payment.failed`, all verified
  via HMAC signature.
- **Scheduling (not built this pass):** One Cloudflare Cron Trigger (every 15 min, requires the
  Workers **Paid** plan — Free plan's 10ms CPU budget can't support this) queries D1 for subscribers
  whose UTC-normalized send-minute matches, pushes IDs onto a Cloudflare Queue; a separate consumer
  Worker does the Claude call + email send per user, with retries + a dead-letter queue.
- **Content generation (not built this pass):** Claude (Haiku 4.5 for cost at scale; Sonnet 5 as a
  quality upgrade option), prompted with rasi/nakshatra + role/profession + date — no raw birth data,
  no per-day astrology API call.
- **Transactional email (not built this pass):** Resend.
- **Encryption:** AES-256-GCM (`src/lib/encryption.ts`). Master key in a Cloudflare secret
  (`ENCRYPTION_KEY`), random IV per field. Decrypted only transiently — once at signup, and inside the
  future queue consumer. No admin/dashboard path ever returns decrypted PII — there is no admin
  dashboard.

### Data model (D1) — `db/schema.sql`

- `subscribers`: id, email_encrypted, email_hash (sha256, unique — dedupe/unsubscribe lookup without
  decrypting), name_encrypted, dob_encrypted, tob_encrypted, pob_encrypted, role_encrypted, rasi,
  nakshatra, pada, preferred_send_minute_utc (plaintext, not sensitive), status
  (trial/active/paused/cancelled), trial_ends_at, razorpay_customer_id, razorpay_subscription_id,
  unsubscribe_token (unique, unguessable), created_at, updated_at.
- `billing_events`: audit trail of Razorpay webhooks (not yet populated — webhook handler not built).
- `delivery_log`: per-send status (not yet populated — cron/consumer not built).

### Flows built this pass

- **Onboarding → trial → billing** (`src/pages/api/signup.ts`): validate → dedupe check by
  `email_hash` → geocode + resolve UTC birth instant → compute rasi/nakshatra/pada in-process
  (`vedic.ts`) → encrypt all PII fields → create Razorpay customer + subscription (5-day trial
  `start_at`) → insert D1 row → return `subscriptionId` + public `razorpayKeyId` to the client, which
  opens Razorpay Checkout to authorize the UPI/card mandate (`src/pages/index.astro`).
- **Unsubscribe** (`src/pages/api/unsubscribe.ts`): token lookup → cancel Razorpay subscription →
  delete the subscriber row immediately → redirect to `/unsubscribed`.

## Design direction (onboarding + privacy pages)

Superseded the original first-pass look with a redesign built against a Figma wireframe the user
supplied, plus the real logo and brand font:

- **Single-card layout:** the entire onboarding experience (logo + Privacy link, heading, form,
  pricing note, consent, button, footnote) lives inside one card — no separate page-level hero
  section. `Base.astro` got `hideTopbar`/`hideFooter` props so the homepage can suppress the shared
  nav/footer in favor of the in-card header/footnote, while `/privacy` and `/unsubscribed` keep them.
- **Logo:** real `StarSync-logo.svg` (`public/starsync-logo.svg`), used site-wide. Its fill is
  hardcoded to the light text color rather than `currentColor` — `currentColor` doesn't inherit
  through an `<img src>` reference, so that would have rendered invisible (black) on our dark theme.
- **Font:** "Google Sans Flex" (Google Fonts) site-wide, replacing Space Grotesk/Inter.
- **Background:** a photo (`public/hero-bg.webp`) rendered through a WebGL2 "particle reveal" cursor
  effect (`src/lib/particle-reveal.ts`) — adapted from Canvas UI's component to sample a plain image
  texture directly rather than their Chrome-only experimental "html-in-canvas" capture API, so it
  works in any WebGL2 browser. Scoped via a named Astro slot (`slot="background"`) as a true sibling
  of the page shell, not nested inside it — necessary because CSS paints non-positioned static content
  and positioned z-index content in different, non-interleaved steps, so a naive nesting made the
  effect either invisible or cover everything depending on the z-index sign.
- **Card styling:** narrowed to `max-width: 560px` (was full-width), black/translucent
  (`rgba(0,0,0,0.55)`) with `backdrop-filter: blur(24px)` over the particle background. No gradient
  accents in text or the primary button anymore — button is solid white with black text; all text is
  white/gray only (no teal/green accents in copy).
- **Date/time fields:** rebuilt as segmented DD/MM/YYYY and HH/MM/AM-PM input groups (matching the
  wireframe) instead of native date/time pickers, with auto-advance and backspace-to-previous between
  boxes; they reconstruct into the exact `dob`/`tob`/`sendTime` string formats `/api/signup` already
  expects, so no backend changes were needed.

**Treat this as settled, not a first pass** — it's been through several rounds of the user's own
visual QA (stacking bugs, dropdown arrow padding, consent-label wrapping, button color) already.

## What's built vs. what's still open

Built this pass (no external accounts needed — the astrology + geocoding pipeline needs zero keys and
is fully runnable today; only Razorpay/Cloudflare credentials are still needed to run signup
end-to-end):
1. Astro project scaffold, `wrangler.toml` (D1 + Queue bindings declared, not yet provisioned).
2. Onboarding page — single page, all requested fields, trial/pricing copy, privacy trust line.
3. Privacy page — plain-language, names every third party that touches data and why.
4. Unsubscribe confirmation page.
5. `db/schema.sql`, `.dev.vars.example` listing every secret needed.
6. `/api/signup` and `/api/unsubscribe` — real, complete logic: encryption, geocoding, in-process
   Vedic chart calculation (no API key required, verified against `astronomia`'s Meeus-algorithm moon
   position with a manual sanity check), Razorpay customer/subscription creation, D1 writes.

Not built this pass (external accounts/infra required first):
- Cloudflare D1 database + Queue actually provisioned; DNS on `familyfirstapps.com`.
- Razorpay webhook handler + `billing_events` population.
- The cron trigger + queue consumer Worker (daily send pipeline) and Resend email templates.
- Claude prompt design/tuning for the actual daily content voice.

## Open Questions

   5-day free trial?~~ **Resolved (docs.razorpay.com):** yes — a subscription with a future
   `start_at` and no upfront amount triggers a **₹5 "authentication transaction," auto-refunded**,
   at mandate setup (docs: `/payments/subscriptions/workflow`, `/payments/subscriptions/faqs`).
   Razorpay's FAQ bundles "card or UPI ID" under this same ₹5 answer, though the answer text itself
   only says "card" explicitly — treat "applies identically to UPI Autopay" as *likely but not
   100% explicitly confirmed* by their docs. Not confirmed: whether the amount differs for UPI vs.
   card, or whether it's configurable to ₹0 (no such parameter is documented). Onboarding copy
   (`src/pages/index.astro`) now discloses this charge upfront.

   deleted immediately regardless).
